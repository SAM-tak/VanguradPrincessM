## 技番号と補助処理

使用キャラ内の元の番号を維持し、サポート種別の基数（10000〜50000）を足した実行番号へ移す。
ゆいのえこ「キック」#478なら10478。本体からの参照と、サポート内のジャンプ・生成・呼出先を対応して書き換える。
命令のブロック位置は変えない。R/RPは技番号ではなく被弾反応表の番号なので移動しない。

補助処理も使用キャラの原作から抽出し、各サポートファイル内へ含める。
途中ブロックへの入口から、条件分岐・呼出し・生成・終了を辿って必要な命令を残す。
補助技の到達しない部分はNopで埋め、元のブロック位置を保つ。
これは別キャラとの差分を作る処理ではなく、原作の呼出先の所属を分離する処理。

特にえりの#353は、サポートから呼ばれるブロック3のEをそのまま保持し、前にあるS29を実行する経路を作らない。
くるみの要求93も、HUD内での分岐先はサポート側へ移し、本体の合体攻撃への分岐だけは本体へ接続する。
別サポートの番号範囲内に置かれた補助処理（かなえから呼ぶ#508途中の効果、ヒルダから呼ぶ#600等）も、その入口から必要な命令を選択パッケージ内へ複製する。
本体＋選択した1ファイルだけで、サポート命令の全参照先が揃うことをPythonテストで確認する。

## 素材と先読み

各定義のmediaは元の使用キャラの素材番号表を指す。
その画像・音声一覧が既にsharedや各サポートの実ファイルを参照しているので、バイナリ素材のコピー・再抽出は不要。
原作のキャラ別パレットと素材番号を保持でき、ゆいの番号や音声へ混ざらない。
この依存関係の復元により、えこ専用として置かれていた`assets/supports/えこ/images/1374.png`はかなえからも使うと判明。
同じ画像を`assets/shared/images/cf478a8c23054a159804c19f3c7358a125fc9f73.png`へ戻し、参照一覧を更新した。
画像内容は変更せず、他のサポート専用素材の配置は維持。

`vp.script.loadFor(path, support)`で、選択したサポートの使用キャラ別ファイルだけを組み合わせる。
`vp.select.scriptFor(name, support)`のキャッシュも組み合わせ別。
同じキャラで別サポートを選ぶ1P/2Pの定義表は独立し、読み込んだ命令データは変更しない。
サポートなし（100）はファイルを追加しない。検証用などの選択未指定（-1）は5種類すべてを組み合わせる。

非同期先読みはこの指定に従って定義ファイルを要求し、その後、本体と選択サポートの画像・音声を列挙する。
列挙のコルーチン分割と型付きTaskは維持した。

## 再生成

```powershell
# 各キャラについて未加工のJSONからgen_script.pyを実行した後:
python tools/fm2k_convert/owner_supports.py data --apply
```

既に分離済みなら、上のコマンドだけで保存した原作中間データから再生成できる。
`share_supports.py assets --apply`も新しい処理へ委譲するため、従来コマンドでゆいへ再統一されることはない。
旧共通化レシピしかない入力は拒否する。`organize_support_media.py`も新しいキャラ別ファイルを読める。
配布処理はdata以下のLTONを含め、_conversionを除く既存規則で50ファイルを収録する。

## 検証

- Python: 元の本体・サポート命令列との対応、呼出先の存在、再生成の同一性、えこのキャラ別攻撃力、えりのS29回避、シエラの更新消費値。
- support-flow: 全10キャラ×25入力、くるみの追加口、CPUのサポート使用、ボス固定サポート、向き・薬莢の回帰。
- selective-preload: 5種・くるみ・サポートなし・同キャラ別サポート・キャッシュ再利用。画像・音声だけでなく要求した定義ファイルも非選択分がないことを検査。
- combat-flow: 連続ガード、多段ヒット制御、メルトショット、ゆい超必殺技最終段、236通りの着地、空中押し合い、画面揺れ。
- async-flow: 選択→VS演出→試合、2P入力、実際のD発動、ポーズ、F8、非同期失敗・中断処理。
- story-flow・match-intro: ストーリーの進行とVS演出中のロード。

原作のすべての技を映像・実機で比較した保証ではなく、元定義を保持する変換と既存回帰テストの検証。

# FPS低下の計測と入力履歴検索の除外判定

2026-10-07。ユーザーから30FPS程度まで落ちるとの報告。未コミットの0085に加え、d97d4c4とその前のd96752eを比較した。言語コア・lhat-loveは変更していない。

## 再現と内訳

LÔVEのRelease実行ファイルで、VSモードのゆい同士をメニューから開始。updateへ0.02秒を渡し、実際のdrawも実行。開始前演出の後も1001描画フレームまで観測し、200描画フレームごとに時間とFPSを記録した。ゲーム更新は1/100秒なので、通常はこの区間に400ゲームフレーム進む。処理を高速に回す非描画テストとは異なる。

| コード | 開始前演出後のFPS観測 |
| --- | --- |
| d96752e | 57 / 63 / 66 / 65 |
| d97d4c4 | 49 / 48 / 39 / 52 |
| 0085未コミット状態（修正前） | 44 / 44 / 36 / 36 |
| 今回の修正後 | 52 / 75 / 75 / 75 |

各値は区間末のlove.timer.getFPSで、平均FPS・最低FPSではない。旧コードはbuild/fps-baselinesへ読み出し、同じ現在のassets/dataと実行ファイルで起動した。作業ツリーのロールバックはしていない。ステージ選択やロード完了時点・OS負荷は完全固定していないため、この表だけから各コミットの厳密な寄与率を算出しない。

修正前のプロファイルでは400ゲームフレームあたりcontrolが1.59〜1.88秒（1ゲームフレーム約4.0〜4.7ms）。update全体は200描画フレームあたり3.09〜3.78秒で、入力が大きな割合を占めた。ほかに技スクリプト、FA接触、FA/FD命中、移動・描画の負荷がある。

入力なしでも各コマンドがtime分の履歴を検索していた。先行入力対応以降の履歴窓に、0085のモード分岐・保持状態の参照が加わり、この既存の重い経路をさらに増やしていた。判定対象を増やしたd97d4c4でも低FPSを再現しており、0085だけが発生源とはいえない。

## 修正

`Fighter.lastButtonPress`へ、各A〜Fボタンマスクが最後に新規押下されたフレームを保存する。複数同時押しはその部分集合も満たす。更新は新規押下があるときだけ、最大63項目で固定。個々の履歴やコマンドごとの配列を追加生成しない。

通常入力と技内COMで「最後のステップに必要なボタン押下が受付窓に一度も存在しない」と分かる場合だけfalseを即返す。可能性があれば従来どおり全履歴を調べるため、先行入力の受付期間、コマンドの優先順位、消費ルールを変更しない。連打・溜め・回転、および方向だけのステップにはこの除外判定を適用しない。mode0で不要だった保持履歴の参照もmode1内へ移した。

修正後のcontrolは400ゲームフレームで0.17〜0.20秒（約0.4〜0.5ms/ゲームフレーム）。安定したVS待機区間のupdate合計は200描画フレームで1.30〜1.48秒となった。

別途、乱数seed=42のCPUデモを600描画フレーム実行。両者が実際に攻撃・被弾する区間でもFPS観測値は68 / 73 / 61、controlは約0.49〜0.68ms/ゲームフレーム。すべてのキャラ・技・環境で75FPS固定という保証ではない。

## 検証と再計測

- `tests/command-modes.lh`: 空履歴、受付窓の最終フレームと期限切れ、方向のみ、同時押しの全部分集合、別フレームの押下を同時押しにしないこと、1024枠の周回後の期限切れを追加。
- yui-link、support-flow、vm-auditで先行入力・連続技・250サポート入力・技内COMを回帰確認。
- `tests/battle-performance.lh`: 通常のmainを通すCPUデモのupdate/draw時間計測。環境依存のFPS合格閾値は設定しない。

詳細プロファイルはルート一時コピーへタイマーを挿入して計測し、本体mainへは混入させていない。コピーはbuildへ保存。ログは `build/fps-current-long.log`, `fps-head.log`, `fps-before.log`, `fps-fixed-idle.log`, `fps-fixed-cpu.log`, `fps-check-*.log`。

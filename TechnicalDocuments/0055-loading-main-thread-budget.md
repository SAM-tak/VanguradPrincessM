# ロード中のメインスレッド停止の計測と分割

## 計測

2026-10-05、`tools/test-async.ps1 -Test async-flow`（ゆい／はるか、キャンセル後の再試行を含む）で計測。試験用タイマーは通常コードには残さず、ログはbuild/load-profile*.logに保存した。

- 素材一覧作成：2人分で181〜227ms。main.completeLoad → Load.ready → Load.assetsでメインスレッド上にまとめて実行されていた。
- ゆいは24,418ブロックを走査し、9,636回mediaを呼び、1,385件を新規登録。はるかは24,092ブロック／9,716回／628件。重複排除は既にあるが、走査と登録要求は重複する。
- 完了済みタスクのfinish：キャラごとに約19〜26ms。さらに分解するとresult fits Dataの再帰型検査が18〜19msで、task.await自体は4ms未満だった。受け取り全体の時間を所有権移譲の時間と混同しない。
- この測定ではnewImage(ImageData)単体の4ms超過を検出しなかった。resource.pumpは既に4ms予算で複数フレームに分けている。

## 修正

Load.assetsをコルーチン化し、1回のreadyにつき2msを目安に進める。技単位、32ブロック単位、画像・音声の列挙途中でyieldする。選択外のサポートをスキップする技走査にもチェックが必要。ここを除外すると約67msの停止が残った。

列挙が中断中でも、その時点までにキューへ積んだIOをワーカーが実行できる。全ジョブが完了するまで列挙の再開を待たない。readyは列挙とIOの両方が完了した場合だけtrueになる。キャンセル済みのLoadは列挙を再開しない。

スクリプト用ワーカーの戻り値をData|nilにし、Job.scriptTaskをstd.task.Task<Data|nil>で保持する。done確認・dispose用の共通Task参照とは別に型情報を維持し、await後はnilだけを判定する。parseはワーカー内で型付きDataを構築するため、メイン側で全構造を再検査する必要はない。unsafeなキャストは使わない。

## 結果と限界

分割と型保持後の同じ遷移テストでは、最長updateが約29〜32msへ短縮した。キャラセレ用音声の技走査にも中断点を追加した最終実行では約15msだった（build/load-sliced-final.log）。約200msの一覧作成による一括停止と約20msの全件型検査は解消。まだキャラセレ素材の到達性解析など、1回の呼び出しを途中で止めない処理があり、2msは厳密な上限ではない。初期化・GPU転送・実行環境による揺れも含むため、全端末のフレーム時間保証ではない。

async-flowで読み込み中断・再試行・実戦描画・画像欠損・型付きスクリプト欠損を確認。selective-preloadで全5サポート、くるみ、サポートなし、同キャラ別サポート、キャッシュ再利用を確認。同期フォールバックなし。

## 全タスクの型保持と実プレイでの停止

実プレイでは強い停止が残るとの報告があり、上記の自動テストの最長updateだけでは解消を判定できない。

追加修正で型引数なしのTask保持先を撤去した。スクリプトはTask<Data|nil>、その他LTONはTask<t^{}|nil>、画像・音声はTask<string|nil>（nilは成功、文字列はエラー）として、生成・保持・awaitまで型を維持する。LTONのテーブル確認もワーカー側で行う。画像・音声本体は引き続きLOVEオブジェクトをチャネルで渡すため、受信時のImageData/Source判定は残る。これは技データ全体の再帰型検査とは異なる。

完了確認と破棄もそれぞれの型付きTaskで行う。型なしの共通Taskへ変換しない。async-flowの欠損試験を画像・音声・通常LTON・スクリプトの4種類へ拡張した。

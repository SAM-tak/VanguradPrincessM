## 測り方

- 原作（`vanpri108/…/ヴァンガードプリンセス.exe`）を起動し、キー入力（P1 の A = `A`、上 = `T`）で対戦まで進める

- 別プロセスから `ReadProcessMemory` で読む。アドレスは wanwan の資料（`docs/analysis/savestate_memory_map.md` など）より:
  - カメラ（視界の左上）`0x447F2C` / `0x447F30`（int32、ピクセル）
  - 1P の位置 `0x4DFCC1` / `0x4DFCC5`、2P の位置 `0x4EDD00` / `0x4EDD04`（16.16 固定小数）
- 読むスクリプトは使い捨て（scratchpad の `peek2.ps1`）。値が変わるたびに記録する（1 フレーム 10 ms より細かく読める）

## そこから分かったこと

1. **キャラは画面から出られない**: x は [カメラ x + 50, カメラ x + 590]。ステージの壁とは別。対戦中の 2 人の距離の最大（実測 550 前後）もこれ
2. **カメラは毎フレーム、目標まで残りの半分だけ動く**（端数は切り捨て）。そして **1 フレーム遅れる**:
   - 動く先は「前のフレームの」キャラの位置から決める
   - キャラを画面の中に止めるのは、カメラが動く前に行う
   - 目標 x は 2 人の中点 − 320（0〜640 に収める）。目標 y は高い方のキャラの y − 320（480 以下）。ジャンプ中にカメラの y が 388 まで上がった
   - この規則で、#21 の間のカメラ（0, 24, 49, 80, 114, 151, 191, 233, 276, 297, 307, 312, 314）と 2P の位置が、実測と 1 フレームずつ一致する
3. **移動は「速度 += 加速度」を先に、「位置 += 速度」を後に**行う。
   逆の順番だと最高点は 223.7 px で、ちょうど初速 1 フレーム分（12.09）高い。0006 の「位置が先」は誤り
4. **I の待ちは、タイマーを「足す」**。前の画像が終わった時点のタイマー（−100、待ち 0 の後は −1）が残るため、
   **エンジンが技を始めた直後の最初の画像だけ N+1 フレーム、その後の画像は N フレーム**になる。
   - 逆コンパイル（`gamespeed_csm_decompile.md` の OP_PIC）も `wait_timer = 100 × keepTime + wait_timer`（足し算）
   - 0006 の「N は N+1 フレーム」は、技の最初の画像についてだけ正しかった
   - 根拠: 上の 3 の「9 フレーム」（#21 の 2 枚目の画像、待ち 9）
   - **DS（着地など）が技を切り替えるときは、タイマーを 0 にする**（逆コンパイルの着地処理: `waitCounter = 0`）。
     これをしなかった間、垂直ジャンプの着地硬直が 111 フレームになっていた:
     垂直ジャンプは最後の画像を待ち 112 で出したまま着地する。その残り（約 11000）に、着地の技 #9 の待ち 2 が足されていた。
     前ジャンプは最後の画像が短いので目立たなかった。直した後はどちらも 7 フレーム
5. ラウンドの時間は **60 秒**（原作の画面の表示）

# 0003: データ移行方針 — KGT 系フォーマットは使い続けない

- **日付**: 2026-09-28
- **状態**: 決定・変換器実装済み（`tools/fm2k_convert/`）

## 決定

- `.kgt` / `.player` / `.stage` / `.demo` は **移行元としてだけ使う**。移植版の実行時には読まない。
- **L^ 側に KGT パーサーは作らない。**
- 一度だけ変換して、移植版のネイティブ形式に置き換える:
  - 画像 → `png`（アニメーションの見本や確認用は `gif` も可）
  - 音声 → `wav` / `ogg`
  - アニメーション・スプライト定義・技・当たり判定・コマンドなどのデータ → **LTON**
    （L^ Table Object Notation。仕様は `lhat/DesignDocuments/08-lton.md`）
- 変換後のデータは自由に手を入れて改善してよい。原作との完全な互換は目標にしない。
- 変換スクリプトは **Python**（Pillow）。
- キャラのカラー違いは **絵を1種類だけ持ち、パレットを差し替えるシェーダー**で表現する。
- ~~パレット番号 0 は透明~~ → **純黒 RGB (0,0,0) が透明**（0007 で訂正）。

## 理由

- 改善・拡張をしたい。KGT 形式に縛られると、エディタの制約（ブロック 16B 固定、パレット 256 色など）まで引き継いでしまう。
- 実行時パーサーは保守の負担になるだけで、利点がない。
- パレット差し替えなら画像容量は 1/8。カラーの追加・改造も palettes.png を編集するだけで済む。

## 変換の流れ

```text
原作データ (2DKGT2G)
  └─ fm2ndparser（ロック判定を外したローカル版） → JSON（画像・音声のバイト列を含む）
       └─ tools/fm2k_convert/convert.py → assets/ に png / wav / LTON
```

手順の詳細は `tools/fm2k_convert/README.md`。

- fm2ndparser は MIT。ロック判定を外すだけで `2DKGT2G` を読める（全38ファイルで確認済み。詳細は 0002）。
- JSON は中間物。リポジトリには入れない。
- `assets/` は原作素材そのものなので、当面 `.gitignore` に入れてある（コミットするかは未決）。

## 出力形式

```text
assets/<system|characters|stages|demos>/<名前>/
  data.lton           設定・コマンド・CPU・ストーリー・組み込み技の対応表など
  images.lton         位置 = FM2K の画像番号、nil^ = 欠番
  sounds.lton         位置 = FM2K の効果音番号、nil^ = 欠番
  skills/NNNN.lton    技 100 個ずつ。技番号 = first + 位置
  images/NNNN.png     indexed: 8bit グレースケール（値 = パレット番号）
                      rgba:    専用パレットを持っていた画像（エフェクト・背景など）
  palettes.png        256×8。1 行 = 1 カラー。番号 0 は alpha 0
  sounds/NNNN.wav     元のバイト列そのまま
```

- 変換結果: 38 ファイル、計約 525MB（大半は非圧縮 WAV）。キャラ 1 体あたり約 2000 枚の画像、約 800 の技。
- 画像番号・効果音番号には欠番がある（ゆいは画像 2028 枚に対して最大番号 3013、欠番 986）。技からは番号で参照されるので、番号を保つ。
- 技番号は連番（欠番なし）。
- fm2ndparser の出力から、派生フィールド（`in`, `fails`, `replace` など他のフィールドから計算できるもの）と、ブロックの `index` を削った。
- fm2ndparser の `type` フィールドにはファイル種別ではなく署名（`2DKGT2G`）が入っている。種別は `.kgt` の一覧（characters / stages / demos）から判定する。

## LTON の書き出しで分かったこと（lhat 0.3.3 時点）

- **ファイルは分割する。** lhat のコンパイラは定数表を線形探索している（`lhat/src/code.c` の `lhat_chunk_constant`）。
  そのため固有の定数が多いファイルは超線形に遅くなる。
  例: images（固有の文字列 2028 個）+ skills を 1 ファイルにすると 4.6 秒。別々なら 0.13 秒 + 1.1 秒。
  また定数は 1 チャンク 65536 個が上限なので、巨大な 1 ファイルはいずれ上限に当たる。
- **`[n] = {…}` の明示キーは避け、位置要素で書く。** 同じ内容で約 5 倍遅い（0.83 秒 → 0.16 秒）。
- 位置要素は **0 始まり**。**`nil^,` を置くと番号が 1 つ進む** → 欠番を穴として書ける。
  （9/20 ビルドの lhat は 1 始まりだった。0 始まりへの変更は 2026-09-21。古いビルドで検証しないこと）
- 結果: キャラ 1 体の LTON は全部で約 1.5 秒（22 ファイル）、1 ファイル最大 0.34 秒。当初の 1 ファイル 4.6 秒から約 1/3。
- 実行時はテキストではなく、コンパイル済みのバイト列（`lhat --compile`）を読むのが前提（08-lton.md 7改）。
- LTON にはまだ公式の書き出し器がない（08-lton.md の未決 T3）。変換スクリプト側で書き出している。
- `nil^` を名前付きの値に書くと、鍵を置かないのと同じ → 名前付きの値では省略する。
- 読み込み: `import^ std.lton` のうえで `std.lton.load(path)`。

## 使う実行ファイル

- LTON の一括検査: `lhat/build/release/lhat.exe --compile`（`clang-release` は古い）
- ゲームの実行と実行時の確認: `lhat-love/build/love/Release/lovec.exe`（LÖVE API の定義を含む）
  - 2026-09-28 の更新で、コンパイル失敗の詳細を表示するようになった
  - `lovec --compile -o <出力先> main.lh` でゲームを実行せずに検査・コンパイルできる（`--compile-game` で丸ごと）
  - `lovec --no-panic-screen .` で、panic 時に青い画面のまま止まらず終了する（自動テスト向き）
- 画面を出さずに確かめたいときは、プロジェクト直下に小さな `.lh` を置いて `lovec that.lh` で走らせ、
  `load` の中で `print` して `love.event.quit()` する（`update` / `draw` の中の `print` は、プロセスを強制終了すると失われる）

## 今後の方針（2026-09-28 決定）

- **ogg 化**: 当分後回し。
- **`assets/` のコミット**: いずれする。ただし次の 2 つが済んでから:
  - LTON の構造改善がある程度進むこと
  - プレースホルダーと思われる無意味な画像を削除すること
- **技の制御は L^ のコードで書く。** LTON のデータを解釈して動かすインタプリタ的な作り（KGT の方式）はとらない。
  技 = L^ の関数・手続きそのもの。LTON に残すのは純粋なデータ（画像表・効果音表・パレット・当たり判定の矩形など）に限る方向。
  → 現状の `skills/*.lton`（fm2ndparser のブロック列の写し）は、L^ コードへ変換するための中間物という位置づけになる。
- **透過**: 純黒 (0,0,0) が透明（0007 で確定・訂正）。

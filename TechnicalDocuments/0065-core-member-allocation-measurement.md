# メンバー検索の一時オブジェクト削減後の再計測

2026-10-06。L^コア開発側の変更を含むLÔVE（`love.dll` 更新時刻12:53:37）で再計測した。この調査ではコア／エンジンのソース変更・再ビルドは行っていない。

## 条件

0064で用いたVSテストと同じフロー：ゆい対ゆい、F2で相手の体力を1にし、実際のラウンド処理で時間切れ2本勝利、キャラセレ→ESC→モード→ESC→タイトル。3試合。シミュレーションを1描画につき最大60回進める加速試験で、実プレイ時のFPS測定ではない。

`LHATOVE_GC_STATS=1` により、毎描画フレームの累計回収数と現在のGC対象数を記録。タイトル復帰後30／90描画で明示的GCを行い、比較点を揃えた。プロセスのprivate bytesは外部から約250ms以上の間隔でサンプリングした観測値であり、瞬間的な真の最大値を保証しない。

- 前回：`build/gc-audit.log`／`.csv`（検索最適化前）
- 今回：`build/core-member-after.log`／`.csv`
- 今回の実行スクリプト：`build/gc-audit.lh` をルートの一時エントリにコピーして実行

前回ログはステージの乱数を固定しておらず、今回は42に固定。弱参照表の修正も含む新しいビルドであり、単一変更だけを切り替えた厳密なA/B測定ではない。GC回収数は一時オブジェクト生成量の目安であって、今回、種別別の生成カウンターは再挿入していない。

## 結果

起動直後の比較用GCから、3試合目のタイトル復帰後90描画のGCまでを集計。

| 指標 | 前回 | 今回 |
|---|---:|---:|
| GC回収数（3試合合計） | 80,907,133 | 73,970,611 |
| 1試合平均 | 約2,697万 | 約2,466万 |
| GC対象数の観測最大（未回収ゴミを含む） | 5,867,270 | 5,741,420 |
| private bytes観測最大 | 1,388.0MB | 1,368.3MB |
| タイトル時private bytes中央値・1周目 | 801.1MB | 781.4MB |
| 同・2周目 | 824.3MB | 825.5MB |
| 同・3周目 | 829.1MB | 820.1MB |
| 3周目GC後のオブジェクト数 | 89,372 | 89,024 |

回収数は約8.6%減少。GC対象数の最大は約2.1%減、プロセスメモリの観測最大は約1.4%減。今回のゲーム全体では、一時生成の削減は見えるものの、メモリ使用量が大幅に下がる変化にはなっていない。起動／終了直前の採取タイミングに左右されるプロセスメモリ最小値を、タイトル常駐量の比較には使っていない。

## 更新時間

別の1試合実行で、テスト用ラッパーから `main.update` を計時した。`build/core-member-timing.log` と `build/core-timing-run.lh`。

- 7,345回のupdate合計：38.4257秒。
- 試合進行側のupdate最大：0.189656秒。
- それ以外（ロード・画面遷移・GCを含む）のupdate最大：0.430914秒。
- 起動から検証完了まで：45.9186秒。

これは1回の観測であり、試合進行側は前後演出も含む。0.430914秒をGC単体の所要時間とは断定しない。前回の0.76秒は異なるCPUデモ検証であり、今回の値との比率を改善率として扱わない。

## 何が減り、何が残るか

コア差分では `vm_lookup_named`／`lhat_table_locate_bytes` により、メンバー名や演算子名を調べるためだけの `LhatString` 確保が不要になっている。

一方、`src/vm_member.c` の `bind_native` は引き続き `lhat_native_new` を呼ぶ。数値・文字列・コルーチン等の組み込みメンバーを束縛するオブジェクトは残る。0064で約8割を占めていたこの生成経路まで今回なくなった、とは解釈しない。

ゲーム側の書き換えや新しい回避策は追加していない。

## 14:02:53再ビルド後：組み込みメンバーの一時束縛を削減

同日、ユーザーが再ビルドした `love.dll`（更新時刻14:02:53、10,185,728 bytes）で再計測。今回もコア／エンジン／ゲームのソース変更・再ビルドは行わず、提供済みバイナリで実行した。

直前の `core-member-after` と**同じスクリプト、キャラ、乱数シード42、3試合、GC比較点**を使用。ログは `build/core-member-rebuilt.log`／`.csv`、集計は `build/core-member-rebuilt-summary.json`。

| 指標 | 12:53版 | 14:02版 | 変化 |
|---|---:|---:|---:|
| GC回収数・3試合 | 73,970,611 | 9,908,560 | −86.6% |
| GC対象数の観測最大（未回収ゴミを含む） | 5,741,420 | 1,764,722 | −69.3% |
| private bytes観測最大 | 1,368.3MB | 1,306.3MB | −4.5% |
| タイトル時private bytes中央値・1周目 | 781.4MB | 766.7MB | |
| 同・2周目 | 825.5MB | 822.2MB | |
| 同・3周目 | 820.1MB | 821.0MB | ほぼ同じ |
| 3周目GC後のオブジェクト数 | 89,024 | 89,026 | ほぼ同じ |

更新時間も同じ1試合用ハーネスで再計測した。`build/core-member-rebuilt-timing.log`。

| 指標 | 12:53版 | 14:02版 |
|---|---:|---:|
| update回数 | 7,345 | 7,299 |
| update合計時間 | 38.4257秒 | 30.7603秒 |
| 試合進行側のupdate最大 | 0.189656秒 | 0.116563秒 |
| それ以外のupdate最大 | 0.430914秒 | 0.312733秒 |
| 起動から検証完了まで | 45.9186秒 | 37.7182秒 |

同じラウンド進行でもロード完了を待つ描画回数が異なるため、update回数は完全一致しない。合計時間は約20%減。各1回の観測であり、FPSの比較でもGC単体の時間比較でもない。

コア差分では、即座に呼び出すメンバーを `GETMETHOD` で扱い、組み込み操作を受け手なしで共有し、呼び出し時にスタック上で受け手を付ける経路が追加されている。これにより、前回残っていた一時束縛の生成が抑えられたことと整合する。

一時生成の削減は大きいが、プロセス全体の使用量はそれほど減っていない。GC対象数はサイズを表さず、プロセス使用量には素材・処理系の常駐領域・ヒープ内の空き領域等も含まれる。今回の測定だけで、残る約820MBの内訳を新たに断定しない。

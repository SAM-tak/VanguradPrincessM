# GC設定の調整

2026-10-06。L^.gc.configure追加と組み込みループの変更後、同日18:33:26のlhat-loveで測定。

## 採用設定

main.lhのloadで、prepare("boot")より前に次を設定する。

```lhat
let^gc = L^.gc.settings()
gc.growth := 120
gc.stepmul := 800
gc.stepsize := 10
L^.gc.configure(gc)
```

次の周期を生存個数の120%＋小さな床で開始し、周期の途中は個数が10増えるごとに約80オブジェクト分処理する。設定はコアの公開APIを使用し、メインVMに加えて以後作られるtaskのVMにも継承される。コア・lhat-loveの実装や既定値は変更しない。

試合中に毎フレームcollect/stepを呼ぶ処理は追加しない。既存のシーン終了後のcollectは維持。collectgarbageからgc.collectへの移行は、この調整開始時に既に作業ツリーへ入っていた変更。

## 比較条件

CPUデモ、seed 42、1描画につきupdate(1/60)を1回、60秒分3600更新。各設定は別プロセスで順番に実行し、同時に別のゲームベンチマークを動かさない。試合開始と毎60更新でOSのprivate bytes/working set、GC統計、画像統計を取得。試合中の明示的フルGCなし。コードのupdateとdrawのCPU経過時間を各フレームで加算し、0.1ms刻みのヒストグラムを採取した。

時刻は更新回数基準であり、ホストの実際の描画レートを60Hzに固定したものではない。CPU時間はpresentやGPU完了待ちを含むフレーム全体の時間ではない。計測用status、統計出力等の共通負荷がある。値は同一環境の各1試合の比較で、厳密な統計的優劣を保証するものではない。

| growth / stepmul / stepsize | 最大working set MB | 最大private MB | 平均update＋draw ms | p95 ms | p99 ms | 最大 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 200 / 200 / 10（既定） | 699.3 | 1136.6 | 7.98 | 13.0 | 20.3 | 109.25 |
| 150 / 400 / 10 | 532.5 | 966.1 | 8.07 | 13.6 | 21.3 | 78.79 |
| **120 / 800 / 10** | **456.2** | **886.3** | **6.91** | **10.4** | **14.0** | **38.59** |

MBは10進。最大メモリは毎60更新のサンプル中の最大であり、その間の瞬間ピークは含まない。p95/p99はヒストグラムの区間上端。最大CPU時間はGC以外の処理・OSスケジューリングの影響も含み、GC単独の停止時間ではない。

採用設定は試合開始時402.2MB、15秒453.2MB、30秒455.5MB、45秒455.5MB、終了時456.2MB。従来の数百MBの増加に対し、約54MB増でほぼ頭打ちとなった。最大値は既定比約243MB（約35%）減。

GC統計のサンプル中最大個数は、既定1,567,419、150/400では853,232、採用設定470,215。試合終了付近の累計cyclesはそれぞれ4、8、21（起動・ロード中も含む）。画像は各実行とも2343個/290,632,484 bytesから2344個/290,665,252 bytesで一致した。描画リソースを減らして得た結果ではない。

## 組み込みループの改善だけでは減らなかった点

最新コアでも既定値は開始時426.1MB→最大699.3MBとなった。一時オブジェクト生成を減らしても、GCがどれだけ溜めてから開始し、どれだけ速く周期を完了するかは別の要因になる。今回の実測では同一ビルドでGC設定を変えることで大きく減少した。

既定値の15秒時点ではcycles=3、phase=pause、個数913,558。回収直後の個数に、その周期中に生成されて次回の判定へ持ち越すものも含まれうる。これは「試合に必要な生存データの量」と同義ではない。0070の明示的GC後約30万個という結果と混同しない。

## 記録と再測定

無視対象build/にgc-tuning-template.lh、run-gc-tuning.py、gc-tuning-{growth}-{stepmul}-{stepsize}.json/.logを保存。ベンチマークは本体load後に比較設定を上書きし、最初のupdateでタスクを起動する前に適用する。採用設定の確認用run-gc-confirm.pyは設定を上書きせず、実際のmain.loadを利用する。

再測定例:

```
tools/fm2k_convert/.venv/Scripts/python.exe build/run-gc-tuning.py 200,200,10 150,400,10 120,800,10
```

## 実装後の確認

設定を上書きしない本体起動経路、別のseed 43で60秒CPU戦を実行。画像2078個/286,284,013 bytesの別組み合わせでも、working setは開始391.4MB、最大445.0MB。平均update＋draw 7.29ms、p99 17.1ms、最大43.83ms。終了後タイトル待機で354.1MB。gc-tuning-confirm-120-800-10.json/.logに保存した。

既存のattract-flowとvs-memory-returnも採用設定で成功。前者はCPUデモ開始・終了・入力による中断・ロードキャンセル・タイトル復帰、後者は通常VS戦の終了→キャラセレ→モード→タイトルを3回反復し、対戦リソース参照とキャッシュが残らないことを確認した。エントリ直起動では../requireの解決に失敗するため、ルートの一時エントリへコピーしてrequireの../だけを除去して実行し、終了後削除した。生ログはbuild/gc-tuned-attract-test.log、build/gc-tuned-vs-test.log。

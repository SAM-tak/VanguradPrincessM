# ボスヒルダの固定サポートとCPUのD入力

## ボスヒルダ

ボスの `ヒルダ.player` と選択サポート「ヒルダ」は別定義である。以前の共通化は技名が一致することを根拠にボスにもゆいの定義を適用してしまっていた。

共通化前のボスには以下の違いがある。

- #451「セレクト」は選択値を調べる前に #688 へ無条件ジャンプする。
- #403 のHUDも #407 の専用経路へ無条件ジャンプする。
- #709 では通常サポートと攻撃要求の割り当てが異なる。
- #710 等では通常サポートと同名でも画像を画面外へ置く指定、生成する演出の位置・開始ブロック、音声などが異なる。

ボスを通常5種の共通化対象から除外し、元の806技をボス自身の定義として復元した。共通化前の保存データ `build/support-originals/ヒルダ/script.lton` を復旧に使用し、欠けていた81個のEB拡張引数は `assets/characters/ヒルダ/skills/*.lton` の抽出データと照合して補った。復旧後の変換入力は `data/_conversion/characters/ヒルダ/support-source.lton` に保存済みで、今後の再生成にbuildのバックアップは不要。

ランタイムは `fixedSupport = true^` と明示し、共有サポートパッケージをリンクしない。元の番号と内部参照を維持するため、今回は未使用候補の技を含めて保持している。ボスの素材先読みもボス自身の全定義を対象とする。専用経路だけに削減する解析は今回行っていない。

`share_supports.py` の再実行でもこの定義を維持する。通常キャラ10名（くるみの追加連携を含む）は従来通り共有する。ストーリーでボスを準備する際は選択サポートをランダムに設定せず100とするが、固定サポートを決定する根拠は元の無条件ジャンプである。

## CPU

従来のBrainは本体の技番号と方向だけを返し、`main.lh` は両側のCPUについてボタン値0を `control` に渡していた。このためサポートHUDのD入力を使うCOM分岐に入れなかった。抽出済みの11キャラのCPU行動表にもDの登録はない。

Brainにサポート使用の判断を追加し、Inputの `buttons = 8` を両側の `control` へ渡す。キャラ変数76やゲージをBrainから直接書き換えず、既存の入力履歴→HUDのCOM→ゲージ処理→攻撃分岐を使う。

現状の判断はL^側の補完実装であり、原作CPUの使用頻度・選択アルゴリズムを再現できたと断定するものではない。

- 開始後100判断フレーム待機。その後の試行間隔は難易度に応じて80〜280フレーム。
- サポートが存在し、生存・ゲージ10以上・要求値99未満・被弾反応中でない場合に入力する。ヒットストップ・ガード硬直中は通常のCPU判断同様に保留。
- 近距離の攻撃判定に4D、空中の相手に2D、遠距離に6D、それ以外に5Dまたは3D。
- 残量による技の変更、攻撃中・クールタイム中の受付制限、消費量は元の技定義が決める。かなえなど、HUDで即時消費しない定義も保持する。

## 検証

- Pythonの26テスト通過。ボスの固定分岐・専用画像指定、内部参照の解決も検証。
- 共通化の再生成計画を作成し、ボスのランタイムがバイト単位で変わらないことを確認。
- `support-flow`：通常10キャラ×5種×5入力、両生成方向でCPUの実D入力から各HUDの要求値・ゲージ処理、空ゲージ時・連続フレームの抑止。
- 選択値101〜105のいずれでもボスの固定経路・専用攻撃へ進み、共有名前空間のオブジェクトを生成しないことを検証。
- `main.lh` コンパイル、`story-flow` 通過。ストーリー回帰ではCPUの共有サポート補助による実ヒットも確認。
- 実画面でのボス戦・原作CPUとの頻度比較は未実施。

# タイトル／CPUデモ反復時のメモリ保持

2026-10-06。数時間の放置で使用メモリが起動時約230MBから10GB超へ増えたとの報告。

## 切り分け

同じプロセスでタイトル→CPUデモ→タイトルを繰り返し、Windows の `PrivateMemorySize64`／`WorkingSet64` と `love.graphics.getStats()` を記録した。テストはソース実行。以下のGBは10進のprivate bytesで、起動直後ではなく反復時の測定値。

- 修正前の短いデモ80周：終了時約3.07GB、観測最大約3.13GB。タイトル時の画像メモリは約55.7MBで一定だった。ログは `build/memory-random.{log,csv}`。
- スクリプトの参照解放だけでは32周時点で約2.25GB。常駐キャッシュ以外に、自動GCでの回収待ちも残る。`build/memory-fixed.csv`。
- 参照解放に加えてタイトル復帰後に明示的GCを行った短いデモ反復では、5周以降の観測範囲約0.80〜1.08GB。`build/memory-collect.csv`。

これらの短いデモは40更新後に終了させるロード／破棄の検証で、実戦の全時間を進めた測定ではない。元の「数時間で10GB」の条件をそのまま再現したとは主張しない。

## 保持していた場所と修正

1. `resource.lh` の `scripts` と `tables` は読み込んだ技定義を永続保持していた。さらに `select.lh` のキャラ＋サポート別の Script キャッシュもそれらを保持していた。
2. スクリプトを要求したBatchごとに利用を数え、そのArenaの終了時に減らすよう変更。最後の利用者が消えたら、解析済み定義と元のLTONテーブルを両方キャッシュから外す。キャッシュヒットにも利用を登録し、旧シーンの終了で新シーンが使う定義を消さない。
3. `Arena.absorb` は素材と一緒に解放処理も受け取る。キャンセルされたワーカーの結果は従来通り保存しない。
4. キャラ＋サポートのScriptラッパーは永続キャッシュをやめ、選択された試合のFighterが保持する。キャラセレの顔グラ用キャッシュは残す。
5. デモ終了時に本体・相手・ステージ・ラウンドの参照を外す。終了処理のスタックが戻った次のupdateで `L^.collectgarbage()` を一度行う。毎フレーム／戦闘中には呼ばない。

画像一覧などの小さいメタデータ、システム素材、描画側のキャッシュは常駐する。OSの確保済み領域もあり、private bytesが起動直後の値へ必ず戻る設計ではない。

## 検証

- `metadata-lifetime`：2つのArenaによる共有、最後の利用者での解放、absorb後の所有権、二重dispose、実行中ロードのキャンセルを確認。
- `selective-preload`：12組み合わせの素材選択に加え、各ケースを破棄すると技キャッシュが0件へ戻ることを確認。
- `attract-flow`、`story-flow`、`match-intro`：入力中断・ロード中断、ストーリー次戦、VS演出と待機を確認。
- `memory-soak`：通常のCPU戦を60秒または決着までシミュレーションし、タイトルへ戻す20周テスト。大きなdt一回で戦闘を飛ばさず、固定ステップを繰り返す。タイトル時の技キャッシュが常駐1件へ戻ること、GPU画像数が常駐分＋描画側の少数の参照に収まることを検査する。ゲーム側の回収以外にテストからGCは呼ばない。

20周完走、終了コード0。タイトル時の技キャッシュは毎回1件、画像数は354〜356、画像メモリは約55.7MBへ戻った。1周目以降のprivate bytes観測範囲は約0.83〜1.32GBで、19周目は約1.16GB。実測ログは `build/memory-soak.{log,csv}`。元の報告と同じ数時間の実時間テストではなく、シミュレーションを加速した検証である。

## 残るコスト

明示的GCを含むタイトル復帰後のupdateには、この検証で最大約0.76秒かかった。メモリの回収を確実にする代わりに、タイトル復帰時の停止がある。GCそのものの段階実行APIを使う変更や言語コアの修正は今回行っていない。今回の結果だけで言語コアのリークとは断定しない。

## 通常対戦から戻る経路の追加修正

初回の修正はデモ終了時だけ参照解除とGCを行っており、通常のVS終了ではArenaを破棄しても `main` のFighter、CPU、Stage、Roundへの参照が残っていた。キャラセレからESCでモードセレクト、さらにタイトルへ戻っても、これらから技定義と実行途中のコルーチンを保持していた。

`releaseBattle` に参照解除を共通化し、通常の試合終了、メニューを戻る操作、F8、ストーリー終了にも適用する。ストーリーの勝敗はRoundを置き換える前に保存する。非同期でモードセレクトを準備する場合は、表示中だったキャラセレの参照を外した後にも次のupdateでGCを行う。

`vs-memory-return` は2P対戦を実際のラウンド処理で2本決着させ、キャラセレ→ESC→モードセレクト→ESC→タイトルを3周する。各試合終了後に対戦データの参照がなくなること、タイトルで技キャッシュが常駐システムの1件に戻ることを確認した。`story-flow` でも勝利後のストーリー進行と次戦開始を確認した。

別実行でも3周完走。外部から100ms間隔で測定した最初の2周では、private bytesは各周の最大約1.36／1.38GBから、タイトル復帰ログ直後のサンプルで約0.80／0.84GBへ減少した。監視は90秒で終了したため3周目終了時のOSメモリ値は未取得。ログは `build/vs-memory-measured.{log,csv}`。この3周だけで長時間の全経路のリーク解消を証明するものではない。

`async-flow` も通過。試合中のポーズからF8で戻った際、対戦データの参照がなくなり、次のupdateで技キャッシュが1件になる検査を追加した。

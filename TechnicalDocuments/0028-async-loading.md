# 0028: 素材と LTON の非同期読み込み

> 更新: コアのマシン別メンバーキャッシュ修正後、2ワーカーで再検証し有効化。以下の1ワーカー制限は初期実装時の記録。修正後の結果は [0029](0029-core-member-race-repro.md) 末尾を参照。

- **日付**: 2026-10-04
- **状況**: 選択画面への遷移は同期読み込み、試合前の先読みもメインスレッドで約6msずつ読み込んでいた。最新の `std.task` の所有権移譲を使い、読み込みとデコードを描画から分離した。

## 実装

- `src/resource.lh`: 専用ワーカー1本、最大16ジョブを投入。`done()` を確認してから `await()` するため、未完了の仕事をメインスレッドで待たない。
- LTON はワーカーで読み込み、スクリプトのブロック・コマンド列も `src/scriptdata.lh` で正規化する。定義インスタンスを使わず通常のテーブルにすることで、結果のグラフを `std.task.await` の所有権移譲で受け取る。大きい表をチャネルでコピーしない。
- 画像はワーカーで `love.image.newImageData(path)`（PNG / R8 DDS）まで処理し、チャネルで参照を渡す。メインスレッドでは GPU テクスチャ生成だけを行う。
- 音声はワーカーで Source を準備し、チャネルで渡す。ループ BGM とオープニング BGM は stream、効果音は static。準備済み Source を clone し、同キャラ対戦でも再生位置を共有しない。
- `src/preload.lh`: メタデータ→参照素材の2段階。共有素材はマニフェストの `shared` を尊重し、indexed 画像が使うパレットも先読みする。顔グラ段階は `portrait.lton` が参照する画像・音声だけを準備する。
- シーンごとの準備アリーナは、読み込み完了時だけスタックへ attach。読み込み中も現在の画面を更新・描画する。ESC で戻ると未投入ジョブを飛ばし、実行中ジョブの完了結果は破棄する。旧シーンの素材と混ぜない。
- 起動時は Loading 表示。システムとカスタムオープニング素材は常駐させる。選択・試合の素材はアリーナ破棄時に解放。小さいマニフェストと正規化スクリプトは再入場用にキャッシュする。
- GPU 転送・結果採用の予算は1更新4ms。ただし単一の転送、結果の採用、シーン構築は分割できず、厳密なフレーム時間の上限ではない。フォントとシェーダーの初回生成もメインスレッドに残る。

## エンジンの対応

lhat-love に `std.task` の登録を追加。Runtime 終了時は task pool を止めてから thread を join し、VM / program を破棄する。署名表・Boot / Nogame バイナリを再生成し、フル版と VM-only Shipping 版をビルドした。ゲームの `lhat-host.json` も更新。

前提はローカルの最新 lhat（HEAD `e31d1d6` に開発中の所有権移譲変更を加えた状態）。lhat-love の `lhat.rev` は更新していない。別環境で再現する場合は、所有権移譲対応のコアと、それに合わせて再生成したエンジンが必要。

## 複数ワーカーの不具合と回避

2本で試合読み込みをキャンセルし再入場すると、結果移譲の拒否やネイティブクラッシュを再現した。ASAN は異なるワーカー T32 / T33 が同じ table backing store を `lhat_table_resize` → `lhat_table_set` → `vm_set_key` → `vm_table_native` から二重解放したと報告。

コア `src/vm.c` の GETMEMBER / CALLMEMBER は、共有 chunk の `member_caches` を検査した後にも `cache->answered` / `index` を読み直す。`src/vm_member.c` の書き込みには同期がなく、同じコードを走る別ワーカーが検査と使用の間に参照先を差し替えられる。メンバ名だけの検査では、異なる表の同名メンバを排除できない。この競合が原因と考えられる。

ゲームでは1本に制限して回避した。描画スレッドとの並行動作、LTON の所有権移譲は維持する。コア自体の修正は加えていない。lhat-love `docs/porting/lhat-issues.md` にも報告を記録。

再現経路は `src/resource.lh` の start を2本へ変更し、`tools/test-async.ps1` を実行。本数を増やすのはコア側の修正と再検証後にする。

## 検証

- `tools/test-async.ps1`: 起動→タイトルスキップ→モード→選択→試合読み込み中にESC→モード→無音タイトル→再選択（ゆい / はるか）→試合を600更新描画→存在しない画像のエラー処理→終了。通過。
- 上の経路の同期フォールバックは LTON / 画像 / 音声すべて0件。通常ビルドの試合到達は起動から約10.1秒（途中のキャンセル・メニュー操作込み）、最大 update 約94ms。読み込み単体のベンチマークではない。
- 1ワーカーで ASAN の同経路を実行し、二重解放は再現しなかった（その時点では未先読みのパレット8件をテストが検出。その後修正し通常ビルドで通過）。
- lhat-love `testing/lh/task`: LTON の移譲、二重 await の拒否、ImageData / Source のチャネル経由受け渡し、タスク破棄後の結果保持、未完了タスクを残した終了をフル版・VM-only Shipping 版で確認。
- エンジン既存 suite: 496/496 通過。ゲーム全キャラ・全ステージの総当たりや配布物全体の再生成は未実施。
